# Нефункциональные требования (NFR) для целевой архитектуры «GoFuture»

### F — Функциональные требования (Functionality)
* **Мультитенантность:** Архитектурная поддержка разделения данных и трафика разных партнеров и регионов в рамках единой платформы.
* **Централизованный аудит фрода:** Реализация сквозной проверки транзакций и бронирований на мошенничество.

### U — Удобство использования (Usability)
* **Доступность документации (Developer Experience):** Наличие интерактивного портала разработчика (Developer Portal) с актуальными спецификациями API (OpenAPI/Swagger) и песочницей (Sandbox) для самостоятельной интеграции партнеров.

### R — Надёжность (Reliability)
* **Доступность (Uptime):** Коэффициент доступности критических сервисов (Booking, Driver, Pricing, Payments, Geography) должен составлять не менее **99,95%** (не более 4 часов 23 минут простоя в год).
* **Время восстановления (MTTR):** Среднее время восстановления системы после сбоя — **< 1 часа** (через 2 месяца) и **< 15 минут** (через год).
* **Отказоустойчивость:** Исключение единых точек отказа. Отказ одного региона или некритичного сервиса (аналитика, фрод и т.п.) не должен вызывать каскадный отказ всей платформы.

### P — Производительность (Performance)
* **Пропускная способность:** Гарантированная обработка до **200 тысяч** одновременных поездок через 2 месяца и более **500 тысяч** через год.
* **Время отклика (Latency):** Задержка обработки геозапросов для динамического ценообразования и «умного» перераспределения водителей в режиме реального времени **< 200 мс**.
* **Эффективность ресурсов:** Снижение затрат на инфраструктуру за счет внедрения автоматического горизонтального масштабирования (Auto-scaling) под нагрузку.

### S — Поддерживаемость (Supportability)
* **Скорость CI/CD:** Время сборки, тестирования и готовности к деплою сокращено с 30+ минут до **< 15 минут** за счет разделения репозиториев сервисов.
* * **Время выхода на рынок (TTM):** Сокращение времени доставки новых функций с 6 месяцев до **2 недель**.
* **Управление контрактами (API Governance):** Все публичные и межсервисные интерфейсы должны быть специфицированы (OpenAPI/Swagger для REST, Proto для gRPC). Тестирование контрактов на обратную совместимость (Backward Compatibility) автоматически в CI/CD-пайплайне.
* **Наблюдаемость (Observability):** 100% покрытие критических доменов метриками и алертами. Внедрение сквозного логирования по Correlation ID между изолированными сервисами.

### + — Дополнительные ограничения
* **Ограничения проектирования (Design Constraints):** Переход от монолитной кодовой базы к распределенной микросервисной архитектуре, где каждый домен владеет своей изолированной БД.
* **Интерфейсные ограничения (Interface Constraints):** Защита API ядра с помощью механизмов ограничения частоты запросов (**Rate Limiting / Throttling**) для внешних партнеров.
* **Локальные регуляторные требования (Legal/Compliance):** Строгое соответствие законам о локализации данных (хранение персональных данных граждан внутри границ соответствующего государства).
* **Требования безопасности (Security):** Централизованное управление идентификацией для сквозной аутентификации пользователей и межсервисного взаимодействия (mTLS / OAuth2).

### Альтернативный вариант ("Большой взрыв") и почему он плох

**Суть альтернативы:** Начать декомпозицию сразу с самого проблемного, нагруженного и критически важного сервиса — Geography (Геопоиск и трекинг) или Booking (Бронирование), так как именно они вызывают каскадные отказы и тормозят бизнес.

Почему так делать не стоит:
1. Высокий риск сломать всё: На первом этапе у команды еще не настроены новые процессы CI/CD, нет опыта межсервисного мониторинга (распределенной трассировки), не развернут API Gateway. Начинать с «сердца» системы — это как делать операцию в неотремонтированной операционной без инструментов.
2. Паралич разработки: Выделение Booking или Geography сразу потянет за собой клубок жестких связей со всеми остальными таблицами монолита (платежи, тарифы, пользователи). Команда увязнет в бесконечных миграциях данных и переписывании кода, полностью заблокировав выпуск новых фич для бизнеса на полгода.
3. Отсутствие авторизации: Если у нас нет выделенного IAM, новый сервис Geography все равно будет вынужден постоянно ходить в монолит, чтобы просто проверить — а имеет ли право этот водитель или пассажир отправлять/запрашивать координаты. Вместо микросервиса получится еще более медленный «распределенный монолит».

## Механизмы обеспечения обратной совместимости.


1. Маршрутизация на API Gateway

API Gateway (Envoy/NGINX) является единой точкой входа и скрывает от потребителей внутреннюю декомпозицию.
* Канареечные релизы: При выделении нового сервиса API Gateway сначала перенаправляет на него лишь 1% запросов, а 99% оставляет на легаси-монолите. Доля плавно увеличивается при отсутствии бизнес-ошибок.
* Маршрутизация по путям: Старые запросы на легаси-урлы а-ля /api/v1/legacy-booking/ -> уходят на GoFuture Monolith. Новые или переключенные шлюзом запросы типа /api/v2/bookings/ -> уходят на новый Booking Service.

2. Предохранительный слой (Anti-Corruption Layer — ACL) на шлюзе

* При необходимости обслуживать старые версии приложений после перехода на новые микросервисы ACL-слой внутри API Gateway может перехватывать легаси-запросы и старые форматы данных (REST/JSON с плоской структурой), на лету пересобирать тело JSON-пакета под требования нового микросервиса (например, gRPC/Proto или новый REST v2), делать вызов в микросервис, получать ответ и конвертировать его обратно в старый формат JSON для приложения.
* Если легаси-клиент присылает некий id внутри объекта запроса, а новый сервис ожидает сложную структуру с региональным контекстом, ACL-слой на шлюзе может дообогащать этот запрос, прежде чем отправить его в микросервис.

3. Стратегия версионирования API и баз данных

* Семантическое версионирование контрактов: Все межсервисные gRPC-контракты и публичные REST API используют strict-версионирование (v1, v2).
* Только аддитивные изменения: Запрещено удалять поля или переименовывать их в рамках одной версии API. Новые параметры добавляются только как необязательные (optional), чтобы старый код не падал при их парсинге.
* Событийная совместимость в Kafka: В шине данных используется Confluent Schema Registry. Микросервисы не могут опубликовать в Кафку событие, ломающее обратную совместимость (Backward Compatibility check). Если формат схемы данных меняется критически, выпускается новая версия топика (например, ride-events-v2).

## Общий алгоритм миграции данных без простоя (Паттерн CDC)

1. Шаг 1. Синхронизация изменений (CDC):
   Разворачивается инструмент (например, Debezium), который непрерывно читает лог транзакций легаси-базы PostgreSQL и стримит изменения таблиц нужного домена в Kafka. Новый микросервис вычитывает эти события из Kafka и записывает в свою изолированную БД. Система находится в состоянии синхронности.
2. Шаг 2. Миграция исторических данных:
   Пока CDC доезжает в реальном времени, запускается пакетный скрипт, который порциями (батчами) переносит исторические данные за прошлые годы из легаси БД в новую БД.
3. Шаг 3. Включение режима двойной записи:
   Когда новый сервис переводится в режим приема операций на запись, он записывает данные к себе, но синхронно или асинхронно дублирует их в легаси-базу (для возможности мгновенного отката в случае сбоя).
4. Шаг 4. Переключение чтения и отключение легаси:
   Когда трафик на чтение полностью переводится на новый микросервис, слой CDC и двойной записи отключается. Таблицы домена в легаси-БД архивируются или удаляются.

### План миграции по конкретным сервисам


1. Домен User Management & IAM (Пользователи) — Выделяется на Этапе 1 (Q1)

* Объем данных: Средний (миллионы строк учетных записей), но критичен для консистентности.
* Что мигрируем: Таблицы пользователей, профилей, сессий, ролей.
* Специфика: Перенос выполняется в первую очередь. Хэши паролей и сессии переносятся один в один, CDC настраивается на таблицы профилей. В момент переключения все сессии остаются валидными за счет сохранения структуры и алгоритмов шифрования в новом сервисе.

2. Домен Geography (Геопозиционирование и трекинг)

* Объем данных: Экстремально высокий (гигабайты геотреков в сутки, миллионы записей координат).
* Что мигрируем: Текущие координаты водителей и полигоны геозон.
* Специфика: Исторические логи координат мигрировать НЕ нужно. Они остаются в легаси ClickHouse для аналитики. Новая база данных (Elasticsearch/Redis для реалтайма) наполняется «с нуля» за счет живого потока координат от водителей. Старая таблица координат в легаси PostgreSQL просто дропается после переключения сервиса.

3. Домены Pricing и Driver (Цены и Водители)

* Объем данных: Высокий (профили водителей, история смен, тарифные сетки).
* Что мигрируем: Профили водителей, документы, автомобили, смены, правила тарифов.
* Специфика: Разделение таблиц водителей (Driver) и заказов (Booking) требует применения паттерна Strangler Fig. В новой базе водителей создается таблица, а старая база монолита начинает обращаться к ней за данными через внутренний API (или напрямую в БД?), пока сам сервис Booking не будет вынесен.

4. Домен Booking (Управление поездками)

* Объем данных: Огромный (сотни миллионов исторических поездок и заказов).
* Что мигрируем: Таблицы заказов, этапов поездок, статусов.
* Специфика: Переносится последним. Исторические поездки (например, старше 1 месяца) переносятся в фоновом режиме порциями по ID. Активные поездки (в статусе «в пути» или «поиск») не трогаются: переключение трафика на новую БД планируется на часы минимальной активности платформы (например, в 3 часа ночи), когда количество конкурентных поездок минимально.

5. Домены Payments и Payouts (Финансы)

* Объем данных: Высокий, критическая важность ACID-транзакций.
* Что мигрируем: Транзакции платежей, инвойсы, балансы водителей и кошельки ЮЛ.
* Специфика: Строжайший аудит балансов. Перед финальным переключением трафика сервис переводится в режим Read-Only на некоторое время для полной сверки сумм (балансов водителей и корпоративных счетов) между легаси PostgreSQL и новыми базами. При совпадении контрольных сумм шлюз переключает трафик.


6. Домен Notification (Уведомления) — Выделяется на Этапе 1 (Q1)

* Объём данных: Низкий (шаблоны, текущие задачи отправки) / Высокий (исторический лог отправленных пушей).
* Что мигрируем: Таблицы шаблонов сообщений и текущие активные токены устройств (PushToken). Историю отправленных уведомлений мигрировать в новую БД не нужно.
* Специфика миграции:
  * Шаблоны переносятся один раз обычным пакетным скриптом, т. к. они меняются редко. 
  * Токены устройств - критически важные данные. Так как токены постоянно обновляются мобильными приложениями, на легаси-таблицу токенов вешается CDC который мгновенно реплицирует новые токены в новую БД PostgreSQL сервиса нотификаций. 
  * Старые логи отправки остаются в легаси-базе монолита как архив. Новый сервис начинает писать лог отправки в свою БД с чистого листа.

2. Домен Analytics (Аналитика данных)

* Объём данных: Экстремально высокий (сотни терабайт исторических сырых событий, метрик и продуктовых логов).
* Что мигрируем: Исторические срезы данных и агрегаты из легаси PostgreSQL, а также перенаправляем живой поток событий из Apache Kafka.
* Специфика миграции: 
  * На этапе запуска живого потока событий новые микросервисы и остаточный монолит уже начинают слать все свои бизнес-события в Apache Kafka. Новый сервис начинает «на лету» читать эти топики и складывать данные в новую аналитическую базу ClickHouse - наполнение реалтайм-данными идет без участия старой БД. 
  * Огромный массив исторических данных уже лежит в легаси-хранилище. Чтобы не перегрузить рабочую легаси-БД при копировании, миграция разбивается на пакетные задачи (например, Spark Jobs), которые выкачивают исторические таблицы порциями за прошлые периоды в часы наименьшей нагрузки на систему. 
  * BI-отчеты (DataLens): Переключение происходит на уровне BI-инструмента. В DataLens создаются новые подключения к целевой Analytics DB (ClickHouse) и дашборды корпоративных менеджеров и бухгалтеров плавно перенаправляются на новые таблицы по мере их готовности.
