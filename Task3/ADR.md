# Текстовое обоснование и архитектурные решения

### 1. Текстовое обоснование выбора регионов развёртывания
Для обеспечения доступности **99,99%** и минимального времени отклика (Latency p99 < 200 мс) платформа «GoFuture» разворачивается по схеме **Multi-Region Active-Active** в трех ключевых гео-зонах на базе инфраструктуры **Yandex Cloud** и локальных инфраструктурных партнеров:
1. **Основной регион (СНГ / Центральная Европа):** `ru-central1` (Москва/Казахстан). Здесь исторически аккумулируется легаси-аналитика компании, сидит команда SRE и развернуты основные мастер-сервисы управления конфигурациями.
2. **Регион Юго-Восточная Азия (ЮВА):** Локальный ЦОД в Сингапуре или Джакарте. Обоснование: минимизация трансграничных задержек. Прямой доступ к локальным картографическим сервисам и платежным API региона (Gcash, GrabPay и др.).
3. **Регион Южная Америка (ЛатАм):** Локальный ЦОД в Сан-Паулу (Бразилия). Обоснование: обеспечение выполнения жестких местных законов по защите данных и удержание Latency для критических процессов заказа такси локальными клиентами в пределах 50-80 мс.

### 2. Схема репликации данных
Так как у нас распределенная топология, использовать классическую синхронную репликацию базы данных между континентами нельзя — задержка сети (RTT) между Бразилией и Сингапуром составляет > 200 мс, что будет тормозить все транзакции.
* **Локальные данные (Booking, Geography, Driver):** Базы данных поездок, текущих координат и смен водителей в каждом регионе работают **изолированно**. Поездка в Бразилии никак не затрагивает базу Сингапура. Данные хранятся локально в региональном PostgreSQL кластере.
* **Глобальные данные (User Management & IAM):** Данные учетных записей пользователей и JWT-сессий требуют сквозной доступности (чтобы пассажир из Бразилии, прилетев в Сингапур, мог войти в приложение). Для них настраивается **асинхронная двунаправленная репликация (Bi-directional/Multi-Master Replication)**.
* **Шина событий (Kafka Cross-Region):** Обмен доменными событиями (например, для сквозного ML-антифрода и сбора глобальной аналитики в ClickHouse) реализуется с помощью инструмента **Kafka MirrorMaker 2**. Он асинхронно реплицирует только выделенные топики (например, `iam-user-events`, `global-fraud-alerts`) между региональными кластерами Kafka через защищенные VPN-туннели.

### 3. Схема реализации геомаршрутизации
Для бесшовного распределения пользователей по ближайшим дата-центрам применяется гибридный подход:
1. **Anycast Routing:** На внешнем периметре регистрируется единый пул Anycast IP-адресов. Запросы от мобильных приложений маршрутизируются до ближайшей точки присутствия (PoP) сети доставки контента и защиты.
2. **GeoDNS (Latency-based Routing):** На уровне авторизованных DNS-серверов активируется функционал маршрутизации по задержкам. Когда приложение делает DNS-запрос `://gofuture.com`, DNS-сервер анализирует IP-адрес источника и возвращает IP-адрес того балансировщика, до которого у пользователя в данный момент минимальный сетевой пинг.
3. **Session Sticky на API Gateway:** Если пользователь перемещается на границе регионов, API Gateway считывает его региональный маркер из JWT-токена и, в случае ошибки геомаршрутизации, прозрачно перенаправляет (проксирует) запрос на слой нужного региона.

# Стратегия комплаенса (Соответствие локальным законам)

При экспансии в Южную Америку (Бразилия — закон **LGPD**) и Юго-Восточную Азию (Сингапур — закон **PDPA**) платформа «GoFuture» использует три архитектурных паттерна для строгого соблюдения регуляторных требований:

1. **Изоляция персональных данных (Data Sovereignty):**
    * Все таблицы, содержащие PII (Personally Identifiable Information — ФИО, телефоны, паспорта водителей, история поездок граждан Бразилии и Сингапура), физически хранятся **только внутри базы данных соответствующего региона**.
    * Запрещено реплицировать эти таблицы в другие регионы (в том числе на центральные сервера в РФ). Локальная база данных региона является единственным первоисточником этих данных.

2. **Деперсонализация при межрегиональной аналитике (Data Masking):**
    * Когда сырые события из региональной Kafka уходят через MirrorMaker 2 в центральный ClickHouse для Spark/Flink аналитики, данные проходят через **слой маскирования (Анонимизации)**.
    * Вместо реального телефона и имени пассажира в глобальную аналитику передается необратимый хэш (`SHA-256(Phone + Salt)`), что делает невозможным идентификацию гражданина за пределами его юридических границ.

3. **Локальное логирование и аудит:**
    * Сбор логов через **Loki** настраивается локально внутри инфраструктурного периметра каждого региона.
    * Логи, содержащие чувствительные данные, имеют строгую политику автоматического удаления (Retention Policy) в соответствии с местным законодательством (например, удаление через 180 дней по требованию регулятора), а доступ сотрудников к ним разграничен жесткой ролевой моделью через IAM.

# Разрешение конфликта между репликацией данных и комплаенсом

Чтобы обеспечить сквозную авторизацию пользователей по всему миру и при этом строго соблюдать законы о суверенитете данных, трансграничная двунаправленная репликация разделяется на два независимых контура.

### 1. Глобальный контур (Что реплицируется асинхронно между регионами)
Между всеми региональными дата-центрами реплицируются **только технические идентификаторы**, которые сами по себе не позволяют установить личность человека (деперсонализированные данные):
* `User_ID` (глобальный уникальный UUID).
* `Password_Hash` (хэш пароля для проверки подлинности).
* `User_Group` / `User_Role` (ролевая модель и уровни доступа).
* Активные сессии (для валидации JWT-токенов в любой точке мира).

Поскольку эти данные обезличены, их трансграничная репликация **не нарушает локальные регуляторные требования**.

### 2. Локальный контур (Что хранится строго внутри границ государства)
Вся чувствительная персональная информация (**PII — Personally Identifiable Information**) хранится **исключительно** в `PostgreSQL` того региона, где пользователь изначально зарегистрировался (домен-донор):
* Реальное имя, фамилия и аватар.
* Номер телефона и Email.
* Токены и реквизиты банковских карт (`UserPaymentProfile`).
* Паспортные данные, лицензии и документы водителей.

### Сценарий: Пользователь из Бразилии прилетает в Сингапур

1. **Бесшовная авторизация:** Пассажир открывает приложение в Сингапуре. Запрос идет на сингапурский `IAM Service`. Сервис сверяет хэш пароля с локальной базой (куда он прилетел по репликации из Бразилии). Проверка успешна — выдается JWT-токен для UUID `456-brazil-user`.
2. **Запрос персональных данных "на лету" (On-Demand):** Когда приложению в Сингапуре необходимо отобразить имя пассажира или его локальный профиль, сингапурский микросервис делает зашифрованный gRPC-запрос напрямую в ЦОД Бразилии, запрашивая данные по UUID `456-brazil-user`.
3. **Изоляция в оперативной памяти:** Данные профиля (Имя, Телефон) передаются по защищенному VPN-туннелю, отображаются на экране интерфейса в Сингапуре и обрабатываются исключительно в оперативной памяти (In-Memory). **Запрещено сохранять или кэшировать эти данные на диски сингапурского ЦОД**.

Это исключает постоянное физическое нахождение персональных данных бразильских граждан за пределами их юрисдикции, полностью закрывая требования комплаенса без деградации пользовательского опыта.
