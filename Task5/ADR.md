# Дизайн мультитенантной платформы «GoFuture»

### 1. Модель изоляции данных между партнёрами (Тенантами)
Для обеспечения полной изоляции данных и исключения рисков утечки информации между партнёрами из разных регионов применяется гибридный паттерн **Database-per-Tenant** (выделенная база данных/схема для каждого партнёра) в сочетании с изоляцией ресурсов:
* **Вычислительная изоляция:** Каждый новый партнёр изолируется на уровне виртуальной сети и оркестратора контейнеров с помощью **Пространств имён (Namespaces)**. Это гарантирует, что процессы одного партнёра не имеют доступа к памяти процессов другого.
* **Изоляция данных:** Микросервисы ядра являются общими (Pool), но логика доступа к данным строго разделена. При онбординге для партнёра создаётся отдельная физическая база данных или изолированная схема в PostgreSQL. Микросервис автоматически переключает контекст соединения (Connection Pool) на нужную БД на основе `Tenant_ID`, переданного в заголовке запроса.
* **Изоляция очередей:** В Apache Kafka для каждого партнёра создаются свои топики с префиксом тенанта (например, `tenant_a.booking_events`). Прямой доступ к чужим топикам заблокирован на уровне политик безопасности (ACL Kafka).

### 2. Автоматизированный процесс подключения новых партнёров (Onboarding)
Процесс онбординга полностью исключает ручную работу инженеров «GoFuture» и выполняется автоматически через **Оркестратор подключения** за 5 последовательных шагов:
1. **Регистрация:** Администратор партнёра заходит на Портал самообслуживания, вводит юридические данные компании, выбирает тарифный план и параметры необходимых квот.
2. **Инициализация безопасности:** Оркестратор обращается в центральный `IAM-сервис` и создаёт там изолированную зону управления (`Tenant Realm`), генерирует SSO-конфигурацию и создаёт первую учётную запись администратора для партнёра.
3. **Нарезка ресурсов и сети:** Оркестратор создаёт изолированный `K8s Namespace`, накладывая на него аппаратные ограничения.
4. **Развёртывание хранилищ:** Автоматически создаётся новая схема/БД в кластере PostgreSQL, и нарезаются выделенные топики в кластере Apache Kafka.
5. **Активация лимитов:** Оркестратор прописывает конфигурацию квот нового тенанта в мультитенантный API Gateway, после чего партнёр может полноценно вызывать API платформы.

### 3. Расширенная система лимитов и квот
Чтобы один крупный или подвергшиеся DDoS-атаке партнёр не мог заблокировать работу всей платформы, API Gateway и инфраструктурный слой контролируют лимиты по четырём направлениям:
* **Сетевые лимиты:** Ограничение количества запросов в секунду (**RPS**) и максимального размера входящего сообщения (**Payload Size**), чтобы исключить перегрузку сети тяжёлыми JSON-пакетами.
* **Вычислительные квоты:** Жёсткие лимиты на CPU и оперативную память (RAM) внутри пространства имён (`Namespace`) партнёра. Превышение лимитов приведёт к деградации только его контейнеров, не затрагивая соседей.
* **Лимиты хранилища:** Ограничение максимального объёма диска под базу данных тенанта.
* **Бизнес-лимиты:** Квоты на максимальное количество одновременно запущенных «конкурентных поездок» в системе для конкретного партнёра.

### 4. Мультитенантный мониторинг
Все собираемые метрики шлюза, микросервисов и баз данных в обязательном порядке маркируются ярлыком `tenant_id`.
* **Мультитенантный Prometheus** агрегирует эти данные, позволяя видеть утилизацию ресурсов каждым партнёром отдельно.
* **Оператор (SRE / FinOps)** через центральную Графану контролирует общую стабильность системы, отслеживает соблюдение партнёрами выкупленных лимитов и собирает данные по утилизации ресурсов для выставления счетов (FinOps-модель). При этом оператор видит только технические метрики и **не имеет доступа к персональным данным клиентов партнёра**. В то же время SRE-инженер партнера может в той же центральной Графане видеть дашборды с данными строго своего контура - ему доступны все  записи мониторинга с "его" `tenant_id`.

### 5. Таблица ролей и уровней доступа (Мультитенантная матрица RBAC)

Все роли партнёров имеют сквозной маркер безопасности `Tenant_ID` и действуют строго внутри изолированного периметра своей компании.

| Роль в системе                                                | К какому домену / данным имеет доступ                                                                                                          | Уровень доступа (Read / Write / Delete)                                                                                      | Зачем нужна эта роль (Бизнес-обоснование)                                                                                                                 |
|:--------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Глобальный SRE / Оператор**<br>*(Сотрудник GoFuture)*       | Общая инфраструктура, настройки API Gateway, мультитенантные метрики Prometheus. **Полный запрет на чтение персональных данных (PII).**        | **Read / Write** (Только управление лимитами, квотами, тарифами и правилами маршрутизации шлюза).                            | Мониторит общую стабильность платформы, предотвращает каскадные отказы от «шумных соседей», распределяет ресурсы и считает затраты для FinOps-отчётности. |
| **Администратор Партнёра**<br>*(Сотрудник компании-партнера)* | Домен управления пользователями (`IAM`) и настройки интеграций **строго своего тенанта**.                                                      | **Read / Write / Delete** (Управление сотрудниками и API-ключами только своей компании).                                     | Регистрирует локальных администраторов, диспетчеров, менеджеров и бухгалтеров своего филиала. Выпускает токены для внешних систем автоматизации партнёра. |
| **Локальный SRE / Аналитик**<br>*(Сотрудник Партнера)*        | Изолированная инфраструктура его Namespace, мониторинг / настройки лимитов и утилизации, метрики Prometheus с меткой `Tenant_ID` его партнера. | **Read / Write** (Только управление настройками своего контура).                                                             | Мониторит стабильность своих контейнеров, логи системы, данные своей схемы БД.                                                                            |
| **Локальный Бухгалтер**<br>*(Сотрудник компании-партнера)*    | Домен `Payouts` (Выплаты водителям) и финансовые дашборды в BI-инструменте **строго своего тенанта**.                                          | **Read / Write** (Формирование реестров выплат, просмотр балансов водителей своего региона). **Запрещено создание поездок.** | Контролирует балансы кошельков местных водителей, проверяет финансовые отчёты по корпоративным клиентам, инициирует выплаты через API локального Банка.   |
| **Диспетчер / Менеджер**<br>*(Сотрудник компании-партнера)*   | Домены `Booking` (Поездки) и `Driver` (Водители) **строго своего тенанта**.                                                                    | **Read / Write** (Просмотр карточек поездок, корректировка статусов заказов в ручном режиме). **Запрещено удаление данных.** | Оперативно решает спорные ситуации на линии, отслеживает «горячие зоны» концентрации машин, контролирует выходы водителей на смены.                       |
| **Локальный Водитель**<br>*(Конечный пользователь партнера)*  | Домен `Driver` (собственный профиль, ТС, документы) и баланс своего кошелька.                                                                  | **Read** (Свои данные, история поездок).<br>**Write** (Изменение статуса смены: Свободен / На заказе).                       | Использует водительское мобильное приложение для прохождения проверок, выхода на линию, получения заказов и вывода заработанных средств.                  |
| **Локальный Пассажир**<br>*(Конечный пользователь партнера)*  | Домен `Booking` (только собственные заказы поездок) и управление своим платежным профилем.                                                     | **Read / Write** (Создание, изменение, оплата и отслеживание своих личных заказов такси).                                    | Пользуется пассажирским мобильным приложением для перемещения по городу и оплаты поездок через доступные в его регионе шлюзы.                             |
